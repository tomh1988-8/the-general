Understand the repository

The General is an R package containing a Shiny application. The current package version is 0.0.0.9000. Run development commands from the repository root: the entry point and some example-data paths depend on that working directory.

The common data helpers are the reference implementation for current behaviour. Export templates reproduce their calculations, including existing quirks. A test proving agreement does not establish statistical suitability; use the statistics guide when deciding whether a rule should change.

Restore a development environment

The current lockfile records R 4.5.2, renv 1.1.4 and 128 packages. Use that R version for parity with the verified environment. The broader R (>= 4.1) declaration is not a claim that every dependency combination has been tested.

  1. Clone the repository and open its root as the working directory. On Windows, install the matching R version and the corresponding Rtools if a dependency must build from source.
  2. Allow the project .Rprofile to source renv/activate.R. In an R session started at the root, restore the lockfile:
renv::restore(prompt = FALSE)
renv::status()
getRversion()
utils::packageVersion("testthat")

The restored testthat version is 3.2.3. Tests require local_mocked_bindings(); an older globally installed testthat is not an adequate substitute for the project library. A first restore needs access to the package sources and may compile packages.

If startup is blocked before you can restore, start R without startup files, then explicitly activate this project:

Rscript --vanilla -e 'source("renv/activate.R"); renv::restore(prompt = FALSE)'

In Git Bash, Rscript may not be on PATH. Replace that command name with the quoted absolute path to the matching Rscript.exe, for example "C:/Program Files/R/R-4.5.2/bin/Rscript.exe" for a system-wide installation. The username and install directory differ on other machines. Quote paths containing spaces.

For Windows path or file-lock problems, stop running app/test processes and use a short working clone outside a synchronised folder, such as C:/src/thegeneral. Keep reports and temporary scripts under the repository's ignored tmp/. Configure temporary directories before starting R if a failing native tool needs a shorter path.

Reference: renv restore(). Restoring installs the recorded environment; it is distinct from changing the lockfile to match whatever happens to be installed.

Run the app and tests

From an R session at the repository root, put development logs under tmp and start the app:

dir.create("tmp", showWarnings = FALSE)
options(the_general.log_file = "tmp/app.log")
shiny::runApp(".", launch.browser = TRUE)

The root app.R calls pkgload::load_all(".", export_all = FALSE) and then the_general_app(). Stop the app before replacing source files; restart after applying a patch.

For the same test entry point used by CI, run:

dir.create("tmp", showWarnings = FALSE)
options(the_general.log_file = "tmp/test.log")
testthat::test_local(stop_on_failure = TRUE)

For a focused change, testthat::test_local(filter = "r-scripts", stop_on_failure = TRUE) runs the exporter test file. Run the full suite before integration when shared behaviour or dependencies change. A browser walkthrough is still needed for interaction changes; passing helper tests does not demonstrate that a modal is usable.

Home's Documentation button opens these guides in a new tab while the app session stays open. The button uses the existing www resource mapping and the relative URL www/docs/index.html. You can also open inst/app/www/docs/index.html directly without starting R.

References: testthat package testing and Shiny testServer().

Follow the data and reactive state

  1. Read the CSV as text. This preserves codes and avoids premature conversion. Suggestions inspect the uploaded values; the reviewed mapping determines conversion.
  2. Convert confirmed roles. Create prefixed columns, normalise missing values, parse measurements/dates and derive time fields. Keep the distinction between missing, zero and excluded values.
  3. Validate the mapped dataset. The ingestion result carries raw_metadata, column_profile, standardized_data, transformation_report, validation, capabilities, schema_review and status. The current user-mapped path can have an empty column_profile.
  4. Expose shared session state. rv$unfiltered holds the full mapped data. rv$data holds the current Home population. Each Apply starts from unfiltered data, not the previous subset.
  5. Calculate per view. The module selects inputs and calls a data helper, then a plot helper or table renderer. View-specific exclusions happen here.
  6. Pin a recipe and recalculate exports. Session pins contain graph type, parameters, title, date and ID, not a frozen copy of rows. Dashboard dispatch and R-script generation must agree about the meaning of those parameters.

Use namespaced UI IDs and shiny::moduleServer() for module changes. Keep calculations independent of a live Shiny session where practical; this makes edge cases testable with small data frames. Do not copy a new calculation into several reactive observers.

Capability flags describe support and reasons but are not consistently used to gate every selector. Several analysis selectors still use Cat_/Num_ prefixes. Validation currently accepts a numeric summary field with at least one finite value and an eligible grouping field with a distinct/non-missing ratio below 0.95. Those are structural checks, not a complete quality assessment.

Make a reviewable change

  1. Define the behaviour first. Record the user action, expected result, relevant population and one concrete example. For a statistic, define its denominator, missing-value treatment, zero/negative rules and rounding.
  2. Inspect the current source and tests. Reproduce the issue with the smallest representative input. Check the helper, UI, dashboard and export paths before choosing where to change it.
  3. Change the responsible layer. Keep statistical computation in helpers and interaction in modules. For exported code, favour readable tidyverse steps and comments explaining the method and population.
  4. Verify the risk introduced. Use hand-calculated expectations as well as agreement with existing helpers. Exercise a real browser interaction when it changes the UI.
  5. Update the relevant guide and example. A changed calculation needs updated descriptions and evaluated results. Do not leave an old validation date attached to newly generated outputs.
  6. Review the diff and integrate. Include why the change is needed, what the user will see, validation evidence and any remaining limitation in the PR.

Create feature branches from main and open pull requests back to main. Keep environment changes separate from feature changes unless the feature requires them.

Do not silently “fix” an existing calculation while formatting exports or writing documentation. For example, changing final-level bars to latest-observed bars, removing substring exclusions, or changing a legacy Surplus rule changes results and needs explicit examples and review.

For changes to exported package functions, keep source documentation and NAMESPACE in sync. Use the project's agreed roxygen tooling if regeneration is required; roxygen2 is not part of the current restored package set, so do not assume it is available.

The 23 September 2026 Windows exporter run passed 48 tests and 328 assertions with no test warnings or errors. Nine standalone scripts executed successfully and matched their dashboard analysis data. The bundled examples retain that evidence. They are synthetic and are not user data.

The exporter tests live in tests/testthat/test-r-scripts.R, with fixtures in helper-r-script-fixtures.R. They include independent checks such as a mean of 226 versus a trimmed mean of 36, plus code labels, escaping, sampling and legacy paths. Preserve both execution checks and independent numeric expectations; comparing two copies of the same mistake is insufficient.

For wider column-suggestion evaluation, use datasets from distinct domains and formats, agreed role labels and a held-out set that is not used while tuning heuristics. Measure correct suggestions by role, false numeric/date suggestions, missing-column suggestions and the number of user corrections. Include ambiguous cases where more than one role is reasonable. The successful messy-books example is a regression fixture; broader generalisation has not yet been evaluated.

Tests should not depend on access to production datasets, external accounts or a running app. Use synthetic fixtures, local temporary directories and explicit package libraries for child R processes. Fix a random seed when repeatability matters, and document any intentional difference from the live sample.

Manage dependencies and CI

The project uses renv with an explicit snapshot and dependency fields Imports, Depends and LinkingTo. Suggests is not included in those snapshot fields. Test dependencies therefore need deliberate handling: a successful test run and an “out-of-sync” message can coexist.

When a dependency really changes, update its declaration, install the intended version, inspect renv::status(), and review the lockfile diff. Keep testthat and its supporting test packages restored. Do not use an unreviewed snapshot merely to silence a status message; it can change the recorded dependency set.

The lockfile also pins openxlsx 4.2.8 to a GitHub commit. Preserve its recorded RemoteSha when reproducing the environment. Matching a displayed version alone does not verify a GitHub-sourced package.

The current r-tests.yml runs on pull requests, pushes to main, and manual dispatches, on Ubuntu 24.04. It installs native build prerequisites, selects R from renv, restores the library, checks the locked R/package versions and GitHub SHAs, then runs testthat::test_local(stop_on_failure = TRUE). A local commit does not start CI; pushing to main does, including a pull-request merge.

Version comparison uses R version objects rather than raw strings: strings such as 4.6.0-1 and 4.6.0.1 can denote equivalent versions. Environment failures name the affected package and write tmp/cip/package_versions.csv inside the CI workspace. There is currently no artifact-upload step for that file.

The local Windows report is not evidence that Ubuntu GitHub CI passed. Inspect the actual PR run before merging under a CI requirement. This repository has no mirroring workflow.

References: renv status() and renv lockfiles.

Independent repository

The source is tomh1988-8/the-general. This repository starts with a fresh history and is developed independently. There is no automatic mirroring or deployment workflow.

Keep work on feature branches, review changes in pull requests targeting main, and inspect the R CI result for the exact commit being merged. Repository access is controlled through GitHub settings.

Use a GitHub noreply address for commit attribution if you do not want a contact email in Git history. Keep local credentials and Posit Connect deployment records untracked. Temporary reports belong in the ignored tmp/ directory.

Diagnose and share a failure

Start with the failing operation and its exact error, then check the environment and relevant data contract. Capture sessionInfo(), the chosen R executable, renv::status() and the mapped column names/types. Keep this material in tmp/. The app's log file can be redirected with options(the_general.log_file = "tmp/app.log") before startup.

The agreed patch workflow uses a Python ZIP saved in tmp/, executed without manual extraction using uv run --no-project python tmp/<patch>.zip. A runner checks compatibility, applies only its declared files and writes requested diagnostics to tmp/share_back.zip. Uploading that ZIP is a separate user action. Re-running a runner after editing its feedback file refreshes the report.

Review diagnostic contents before sharing: logs can contain local paths and column names, and dashboard R exports can contain the full mapped population for line comparisons. Use a small synthetic reproducer for a data-specific defect. Do not commit throwaway reports, credentials or private datasets, and do not replace the repository's README with a patch instruction file.

Prepare a release or deployment

For a release, restore the intended environment, run the relevant tests and full suite, review the actual CI result and smoke-test the core workflow: upload, column correction, filter, a table, each changed graph, pin, preview and downloads. Check documentation links and keyboard/narrow-screen behaviour when UI or assets change.

A package build/check adds coverage that the current CI test command does not provide. If distributing an installed package, verify that example data and assets are included and reachable: the current build ignore excludes the root data/ directory, while development uses files from it. Running successfully from a clone does not prove an installed build is self-contained.

The existing Dockerfile starts from rocker/r-ver:4.4.2, which differs from the current R 4.5.2 lockfile. Treat it as an outstanding deployment mismatch to resolve and test before use. The application entry point has no configured authentication boundary; hosting and access controls must be chosen for the deployment's audience and data.

Document the deployed revision, environment and recovery procedure. Keep data transformations and user-visible statistical changes clear in release notes so an analyst can explain why results changed.

Maintain these guides

The canonical sources are three editable HTML files and a shared stylesheet under inst/app/www/docs/. There is no documentation build dependency. Keep headings and fragment IDs stable when linking between guides, give tables captions and header cells, and include meaningful alt text for figures. Local assets make the guides usable without a network connection; external references are optional reading.

The supplied documentation runner validates local links, fragments, duplicate IDs and required asset structure. It is not a complete accessibility audit or a statistical test suite. Open the pages at desktop and phone widths after a layout change, and use print preview if changing the print stylesheet.

When replacing the worked example, regenerate all nine standalone outputs, compare them with the current dashboard helpers, inspect the figures and update the recorded date and results together. Keep example data synthetic. Maintain the existing repo README independently; this documentation patch does not edit it.
